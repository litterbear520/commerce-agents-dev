05 · UML class

继承与三种注入方式

基类只放两个角色逐字相同的代码。角色之间不同的部分，按性质分三种方式交给子类或调用方。

注入方式放什么例子什么时候定下来
类属性数据：每个角色一份、不会变fence = STOREFRONT_FENCE、displayed_text、unavailable_text写类的时候
钩子方法行为：基类知道什么时候调，但不知道怎么做handlers()、memory_subject、domain_error()、absent_tools()子类覆盖
构造参数运行时对象：每个会话 / 部署都不同backend、config、session、state、memory实例化的时候（每轮 stream_turn 新建一个执行器）

06 · Sequence

一次工具调用的全程

以购物角色调用 search_products 为例。商户的 search_listings 走完全一样的路，只是第四、五条生命线换成 MerchantToolExecutor 和 MerchantBackend。

Eager dispatch

块闭合就开跑

  • StreamedRound.relay 边转发流边看块：一个 tool_use 块的参数一闭合，就交给 EagerDispatcher.dispatch 起一个任务。
  • 模型还在写下一个块时，第一个工具已经在查后端了。
  • 流结束后 collect 统一收结果；异常路径由 cancel 兜底。

Provenance + fence

先记溯源，再过围栏

  • remember_products() 把返回的 id 记进 state.seen_products，之后 check_provenance 只认这里面的 id，编造的 id 加不进购物车。
  • _fenced() 调 Fence.fence_payload：清洗、截断、包进围栏，外部文本只能当数据。

Back to the loop

结果兵分两路

  • outcome_events 变成 SSE 事件发给前端。
  • tool_result_block 追加进 messages，下一轮请求带给模型。
  • execute 从不抛异常，失败也是一个 ToolOutcome。

07 · Flowchart

dispatch 的路由顺序

上面时序图里 “dispatch() 按名字路由” 这一步展开来看。顺序本身就是规则：先拦配置关掉的工具，再看是不是技能、展示组件，最后才查角色的 handler 表。

execute() = try + dispatch()

失败分三级

  • InvalidArguments（parse_argument 抛出）→ “参数无效——哪些字段”，让模型改参数重调。
  • domain_error(error) 钩子返回非 None → 用角色自己的说法。购物把 NotOffered 映射成 “不是本店提供的”，Unavailable 映射成 “未加入购物车，推荐有货替代品”；商户暂时不覆盖。
  • 其他异常 → 记日志，回 unavailable_text：“暂时不可用，用已有信息继续”。

Why dispatch 单独存在

预取需要看见异常

  • dispatch 不做失败分级，异常直接往上抛。
  • 预取读数据的调用方要分清 “工具失败了” 和 “工具自己写了结果”，所以用它而不是 execute。
